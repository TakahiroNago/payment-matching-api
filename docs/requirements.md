# 入金消込 API — 要件定義書

- 版：v0.5（2026-11-18）
- 状態：MVP 実装済み。v0.1 からの変更は §10、v0.2 からの変更は §11、v0.3 からの変更は §12、v0.4 からの変更は §13。
- 関連：[api.md](api.md)（API リファレンス）、[../README.md](../README.md)（動かし方と設計判断）

この文書は個人開発・学習目的のものです。題材は一般的な経理業務の入金消込で、特定企業の製品の再現ではありません。データはすべて架空です。

---

## 1. 目的と背景

### 1.1 目的
請求（売掛金）と銀行入金の明細を突き合わせ、どの入金がどの請求に対応するかを判定・記録する API を作る。

### 1.2 示したいこと（優先順）
1. Rust で API サーバーを設計・実装できる（ルーティング、入力検証、エラー設計、認証、テスト）。
2. PostgreSQL のスキーマを設計し、整合性を DB の制約とトランザクションで守れる。
3. 読みやすく、壊れにくく、テストしやすいコード。判定ロジックは I/O から切り離した純粋関数にする。
4. 経理実務の知識を仕様に落とし込める。

### 1.3 解決する業務上の課題
- 振込名義が請求先の正式名称と一致しない（半角カナ、法人格の略語、支店名や担当者名の付加）。
- 1 回の入金で複数の請求をまとめて支払う（合算入金）。
- 振込手数料を差し引いた金額で入金される。
- 同じ明細を 2 回取り込むと二重計上になる。
- なぜその請求に消し込んだかを後から説明できない。

## 2. 範囲

### 2.1 対象（MVP）
1. 取引先・請求の登録と参照
2. 入金明細の取り込み（JSON。冪等）
3. 自動突合（規則 R1〜R4、§4）
4. 候補の確定、手動消込、取消
5. 確定時の振込名義の別名登録
6. 請求・入金の一覧（状態で絞り込み）
7. 静的ベアラートークンによる認証
8. マイグレーション、結合テスト、CI、Docker Compose

### 2.2 対象外
- 画面（UI）、利用者・ロール管理、マルチテナント
- 銀行 API 連携、全銀フォーマットや CSV の解析（取り込みは JSON のみ）
- 分割入金（1 件の請求を複数回に分けて支払う）、過入金の返金・前受金処理
- 外貨、消費税の計算、仕訳の生成
- あいまい一致、AI・機械学習による判定（規則は決定的で説明可能なものに限る）
- 請求・取引先の更新と削除
- 公開環境へのデプロイ

## 3. データモデル

金額はすべて円の整数（`BIGINT`、Rust では `Yen(i64)`）。浮動小数点は使わない。ID はアプリケーションが生成する UUID v7（時刻順に並ぶので、`ORDER BY id` が作成順になる）。

| テーブル | 主な列 | 制約 |
|---|---|---|
| `customers`（取引先） | `id`, `name`, `name_kana`（振込名義の読み）, `fee_deducted`（手数料を差し引いて振り込む取引先か） | 文字数 1〜200 |
| `customer_aliases`（取引先を特定する名義） | `id`, `customer_id`, `alias_raw`, `alias_normalized`, `source`（`kana`＝取引先のカナ名／`manual`／`learned`） | `alias_normalized` は一意で空でない |
| `invoices`（請求） | `id`, `customer_id`, `invoice_number`, `amount`, `due_date`, `status`（`open`／`cleared`／`void`） | `amount > 0`、`invoice_number` は無効でない請求の中で一意 |
| `payment_batches`（取り込み単位） | `id`, `idempotency_key`, `request_hash` | `idempotency_key` は一意 |
| `payments`（入金） | `id`, `batch_id`, `line_no`, `paid_on`, `amount`, `payer_name_raw`, `payer_name_normalized`（正規化できなければ空）, `status`（`unmatched`／`suggested`／`matched`）, `decision`（JSONB：自動判定とその根拠）, `decided_at`（その判定の時刻） | `amount > 0`、`(batch_id, line_no)` は一意 |
| `matches`（消込） | `id`, `payment_id`, `rule`（`R1`〜`R4`／`manual`）, `state`（`suggested`／`confirmed`／`cancelled`）, `fee_amount`, `confirmed_at`, `cancelled_at`, `cancel_reason`（`dismissed`／`reversed`／`replaced`／`invoice_cleared`／`invoice_voided`） | `fee_amount >= 0`、`cancel_reason` は `cancelled` のときだけ |
| `match_allocations`（消込の内訳） | `match_id`, `invoice_id`, `amount`（その請求に充てた入金額） | 主キー `(match_id, invoice_id)`、`amount > 0` |

取引先自身のカナ名も `customer_aliases` に `source = 'kana'` として入れる。「ある名義がどの取引先を指すか」を 1 つのテーブルと 1 つの一意制約で決めるためで、取引先名と別名が別々の取引先を指す状態を作れない。

状態を表す列は `text` と `CHECK` 制約で持つ（PostgreSQL の enum 型は後のマイグレーションで値を変えにくい）。

### 3.1 不変条件と、それを守る場所

| | 不変条件 | 守る場所 |
|---|---|---|
| I1 | 1 件の入金について、取り消されていない消込は 1 つまで | 部分一意インデックス `matches (payment_id) WHERE state <> 'cancelled'` |
| I2 | 1 件の請求が含まれる確定済みの消込は 1 つまで | `UPDATE invoices SET status = 'cleared' WHERE id = ANY(..) AND status = 'open'` の更新行数を請求の件数と比べる。足りなければ 409 でロールバック |
| I3 | 確定済みの消込では「内訳の合計 = 入金額」かつ「内訳の合計 + 手数料 = 請求額の合計」 | 確定のトランザクション内で検証。自動判定についてはプロパティテストでも検査 |
| I4 | 状態の値は決められたものだけ | `CHECK` 制約 |
| I5 | 候補（`suggested`）が指す請求は `open` のものだけ | 請求を `cleared` または `void` にする処理が、同じ請求を含む他の入金の候補を取消にし、その入金を `unmatched` に戻す |

入金の `status` は消込から決まる（確定済みの消込があれば `matched`、候補があれば `suggested`、どちらもなければ `unmatched`）。これと I1〜I3、I5 は、操作を無作為な順に実行して 1 回ごとに SQL で検査する結合テストで確かめる（`tests/api.rs` の整合性テスト）。

消込の状態を変える処理（取り込み、確定、手動消込、取消）は、トランザクションの先頭で同じ advisory lock を取り、直列に実行する。取り込みは「取引先の未消込請求を読んで判定する」処理で、確定は「請求を消し込む」処理なので、並行させると行ロックの取得順を全経路で揃える必要がある。1 つのロックにすればその検討が不要になる。処理量が増えたら取引先単位のロックに分ける。I2 の条件付き UPDATE は、このロックに頼らなくても成り立つ最後の歯止めとして残す。

ロックを待つ時間には上限を置く（接続の `lock_timeout`、5 秒）。待っている要求は接続プールの接続を 1 本ずつ持つので、上限がないと、書き込みの列が接続を使い切って参照や `/readyz` まで失敗する。超えた要求は何も書き込まずに 503（`busy`）で返し、呼び出し側が再送する。接続を取得できなかった場合も同じ 503 にする。

## 4. 突合の規則

### 4.1 振込名義の正規化（純粋関数）
1. Unicode NFKC（半角カナ → 全角カナ、濁点の合成、全角英数 → 半角）
2. 空白を除去。ひらがな → カタカナ、小書きのカナ → 大書き（銀行の名義は小書きを使わない）、英字 → 大文字
3. 括弧つきの法人格の略語を除去（`カ)…`、`…(カ`、`(カ)`。㈱ は NFKC で `(株)` になる）
4. 区切り文字を除去（括弧、中点、ピリオド、スラッシュ、ハイフン類、長音記号）。長音はハイフンで代用されることが多いので、両方とも落として揃える
5. 先頭・末尾の法人格（`カブシキガイシヤ`、`株式会社` など）を除去
6. 結果が空なら「正規化不能」

正規化した結果をもう一度正規化しても変わらない（冪等）。保存したキーをそのまま比較に使うための条件で、プロパティテストで検査する。

略語と法人格の対応表はコード内の定数。表にない表記、支店名や担当者名のついた名義は、別名の登録で吸収する。正規化は完全ではない。

### 4.2 取引先の特定
正規化した名義が `customer_aliases.alias_normalized` に完全一致する取引先。部分一致・あいまい一致は行わない（誤消込のほうが、人の確認待ちになるより害が大きい）。

### 4.3 規則（上から順に評価し、最初に成立したものを採用）

| 規則 | 条件 | 説明が 1 通り | 説明が複数 |
|---|---|---|---|
| R1 単一一致 | 取引先を特定でき、その未消込請求に入金額と同額のものがある | 自動確定 | 支払期日が最も古いものを候補に |
| R2 合算一致 | 取引先を特定でき、未消込請求 2 件以上の合計が入金額に一致する | 自動確定 | 古い請求を優先した組み合わせを候補に |
| R3 手数料差引 | 取引先の `fee_deducted` が真で、R1・R2 の条件が「入金額 + 手数料」で成立する。手数料は設定値のいずれか（既定：110〜880 円の 110 円刻み） | 候補 | 候補（最小の手数料・古い請求を優先） |
| R4 金額のみ | 取引先を特定できず、いずれかの取引先の未消込請求に同額のものがある | 候補（最大 5 件を根拠に記録） | 同左 |

どれも成立しなければ `unmatched`。

- 自動確定するのは、その規則での説明が 1 通りのときだけ。R3 と R4 は 1 通りでも人が確定する。
- R1 は R2 より優先する。同額の請求が 1 件あれば、他の請求の合計が同じ額になっていても R1 で確定する。
- R2 と R3 の組み合わせ探索は、取引先の未消込請求が 20 件以下のときだけ行う。超えたら探索を飛ばし、その旨を根拠に記録する。
- 探索は請求を古い順にたどり、前半の請求を選び終えた時点で「残りの額が後半の請求の部分和にあるか」を確かめて、ない枝を捨てる。後半の部分和は取引先ごとに 1 回だけ求める。n 件に対して手数はおよそ 2^(n/2) で済む（総当たりは 2^n）。取り込みはロックを持ったまま判定するので、判定の遅さは全体の待ち時間になる。
- 手数料は、消込の中で支払期日が最も古い請求から引く。その請求の額が手数料以下になる説明は採用しない。
- 判定は `decide(amount, payer, config) -> Decision` の純粋関数で、DB に触れない。請求の並び順に依存しない。

### 4.4 取り込み
- 1 回の取り込みは 1 トランザクション。行を上から順に判定するので、後の行は前の行が消し込んだ請求を見ない。
- 候補（`suggested`）は請求を消し込まない。同じ請求が複数の入金の候補になることがあり、先に確定したほうが勝つ。負けた候補は取消になり、その入金は `unmatched` に戻る（I5）。

### 4.5 手動操作
- **候補の確定**：`suggested` → `confirmed`。請求が既に消し込まれていれば 409。
- **手動消込**：消込済みでない入金に対し、請求と手数料を指定して確定する。請求はすべて同じ取引先で、「請求額の合計 − 手数料 = 入金額」でなければ 422。入金に候補があれば、その候補は取消になる。
- **取消**：確定済みの消込を取り消すと、請求は `open`、入金は `unmatched` に戻る。候補を取り消す（却下する）と入金は `unmatched` になる。取り消した消込の行は履歴として残る。
- **別名の登録**：確定・手動消込のときに指定すると、入金の正規化済み名義をその取引先の別名（`learned`）として登録する。名義が既に別の取引先のものなら 409 で、消込も行わない。

### 4.6 再判定

自動判定は取り込みのときに、その時点の別名と未消込請求に対して行う。その後に別名を登録した、請求を後から登録した、候補が他の入金に請求を取られて取消になった、という場合のために、`unmatched` の入金を判定し直す操作を置く（`POST /v1/payments/rematch`）。

- 規則と順序は取り込みと同じ（古い入金から順に判定し、前の入金が消し込んだ請求は後の入金に見せない）。取り込みと同じ処理を通す。
- 名義は元の文字列から正規化し直す。正規化の規則を足した後にも効くようにするため。
- `decision` は新しい判定で置き換え、`decided_at` に時刻を残す。「なぜこの状態か」は常に最後の自動判定で説明する。
- 対象は `unmatched` だけ。`suggested` は人が確定か却下をする（却下すれば次の再判定の対象になる）。
- 自動では行わない。確定の応答の裏で別の入金が自動確定されると、操作した人から見えないため。呼び出す側が、別名の登録や確定の後に明示的に呼ぶ。

### 4.7 取消の理由

消込が `cancelled` になる経路は 5 つあり、`matches.cancel_reason` に残す：人が候補を却下した（`dismissed`）、人が確定済みの消込を取り消した（`reversed`）、人が候補の代わりに手動消込をした（`replaced`）、候補の請求が他の入金で消し込まれた（`invoice_cleared`）、候補の請求が無効にされた（`invoice_voided`）。最後の 2 つはその入金への操作ではないので、理由がないと履歴から区別できない。

### 4.8 登録の訂正

登録を間違えたときに、DB を直接触らずに直せるようにする。

- **別名の削除**（`DELETE /v1/customers/{id}/aliases/{alias_id}`）。間違った別名は、その名義の入金を以後ずっと R1・R2 で自動確定させるので、消せないと害が続く。取引先自身のカナ名は消せない（取引先の登録そのものの訂正になる）。既にできた消込や候補は変えない：どれが間違いかは人が判断し、消込の取消で直す。
- **請求の無効化**（`POST /v1/invoices/{id}/void`）。行は消さず `status` を `void` にする。取消済みの候補が請求を指していることがあり、履歴を残すため。未消込の請求だけが対象で、消込済みなら先に消込を取り消す。この請求を含む候補は I5 に従って取消にする。請求番号は無効でない請求の中で一意とし、同じ番号で登録し直せる。元に戻す操作は置かない（登録し直せば足りる）。

## 5. API

一覧と各エンドポイントの入出力は [api.md](api.md)。ここには方針だけを書く。

- 基底パス `/v1`、JSON。認証は `Authorization: Bearer <token>`（定数時間比較）。`/healthz`・`/readyz` は認証なし。
- エラーは RFC 9457（`application/problem+json`）。`type` は `about:blank` に固定し、機械が分岐するための `code` を拡張メンバーとして返す。入力の誤りは `errors: [{ field, code }]`。
- 500 の応答には原因を書かず、`request_id` だけを返す。原因はログに残す。
- 状態コード：400（JSON として読めない、必須ヘッダーがない）、401、404、409（冪等キーの再利用で内容が異なる／同じ内容が取り込み済み／状態が合わない）、413、415、422（形や値が不正）、500、503（`/readyz` で DB に届かない／混んでいて受け付けられない／30 秒を超えた）。
- ハンドラーがパニックしても接続を切らず、500 と `request_id` を返してログに残す。
- 一覧はカーソル方式（`cursor` に最後の ID）。`limit` は既定 50、最大 200。
- 取り込みは 1 回 1,000 行まで、本文 1 MiB まで。

### 5.1 冪等性
- `Idempotency-Key` と、リクエストの内容の SHA-256 を `payment_batches` に保存する。ハッシュは解析した内容を書き出し直したものから取るので、空白やキーの順序が違っても同じ内容なら同じリクエストとみなす。
- 同じキー・同じ内容の再送は何も書き込まず、200 と `replayed: true`、そのバッチの現在の状態を返す。
- 同じキー・異なる内容は 409。
- 別のキー・同じ内容も 409（`allow_duplicate: true` で取り込める）。キーはクライアントが決めるので、リクエストごとに新しいキーを作る実装では、同じ明細の再送をキーでは見分けられない。2 回目の入金は、その時点で未消込の同額の請求（毎月同額の取引先なら翌月分）に自動確定されてしまう。検出するのはバッチ全体の一致だけで、行の一部が重なる場合は対象外。
- 取り込みが途中で失敗したら何も残らない。キーも消費されない。

## 6. 非機能要件

| 項目 | 要件 |
|---|---|
| 言語・主要クレート | Rust（安定版、edition 2024）、axum、tokio、sqlx（`query!` 系のコンパイル時検査と `.sqlx` のオフラインデータ）、serde、thiserror、tracing、time |
| DB | PostgreSQL 17。マイグレーションは `sqlx migrate` またはバイナリの `migrate` サブコマンド。サーバーは起動時に自動適用しない |
| 構成 | `domain`（型・正規化・判定。I/O なし）／`repo`（SQL）／`service`（トランザクション）／`http`（ルーティング・検証・エラー変換） |
| 型 | ID はテーブルごとの newtype、金額は `Yen`。取り違えをコンパイル時に防ぐ |
| 設定 | 環境変数のみ（`DATABASE_URL`、`API_TOKEN`、`BIND_ADDR`、`FEE_AMOUNTS`、`DB_MAX_CONNECTIONS`）。起動時に検証し、不足・不正なら起動しない。トークンは 16 文字以上 |
| ログ | JSON。リクエストごとに `request_id`、メソッド、パス、状態コード、所要時間。本文・クエリ・振込名義・金額・トークンは出さない |
| 停止 | SIGTERM／Ctrl-C で新規受付を止め、処理中のリクエストを待ってから終了 |
| 安全性 | `unsafe` 禁止、`unwrap`／`expect` はテストのみ、SQL はすべてバインド変数 |
| 配布 | 多段ビルドの Dockerfile（distroless、非 root）、`compose.yaml`（api + db） |

## 7. テストと CI

| 種類 | 内容 |
|---|---|
| 単体 | 名義の正規化（事例 39 件）、判定の各分岐、設定の検証、ページング、トークン比較 |
| プロパティ（proptest） | 正規化の冪等性。判定結果の請求は重複せず、合計が「入金額 + 手数料」に等しく、内訳の合計が入金額に等しい。自動確定は説明が 1 通りのときだけ（総当たりと比較）。請求の並び順に依存しない |

## 9. 拡張するなら

- **分割入金・過入金**：`invoices` に消込済み額を持たせ、`match_allocations.amount` を請求額より小さくできるようにする。I2 は「内訳の合計 ≤ 請求額」に変わる。
- **再判定の範囲**：`suggested` の入金も判定し直す（別名を覚えた後、R4 の候補が R1 の自動確定に変わりうる）。同じ結果なら消込を作り直さない比較が要る。
- **取り込み形式**：全銀フォーマット・CSV の解析を `http` の手前に足す。`service` 以降は変わらない。
- **並行性**：advisory lock を取引先単位に分ける。
- **OpenAPI**：`utoipa` で型から生成し、`docs/api.md` を置き換える。
- **利用者と監査**：誰が確定・取消したかを `matches` に記録する。

## 10. v0.1 からの変更

| 項目 | v0.1 | v0.2 | 理由 |
|---|---|---|---|
| 取引先の名義 | `customers.name_normalized` | `customers.name_kana` を追加し、正規化したキーは `customer_aliases`（`source = 'kana'`）へ | 漢字の正式名称はカナの振込名義と一致しない。名義の一意性を 1 つの制約で守る |
| 楽観ロック | `invoices.version`・`payments.version`、`If-Match`、412 | 廃止 | 確定は消込 ID を指定し、状態が `suggested` でなければ 409 になる。直列化と条件付き UPDATE で足り、`If-Match` が守るものが残らなかった |
| 判定の根拠 | `matches.reason` | `payments.decision` | 消込が作られない `unmatched` にも根拠を残すため |
| 複数の説明があるとき | R2 は `unmatched` | 古い請求を優先した候補 | 毎月同額の請求がある取引先では頻繁に起こり、候補を出したほうが人の作業が減る |
| I2 の守り方 | `SELECT … FOR UPDATE` | advisory lock による直列化＋条件付き UPDATE の行数検査 | §3.1 |
| 取消 | 確定済みのみ | 候補の却下にも使う | 候補を残したままにしない手段が必要 |
| カーソル | `(created_at, id)` | `id` のみ | UUID v7 は時刻順 |
| OpenAPI | 自動生成 | 手書きの `docs/api.md` | v0.1 §2.2 で決めた、落とす順の 1 番目 |
| 日付の型 | 未定 | `time` クレート | cargo-deny が `chrono` をメンテナンス終了の勧告（RUSTSEC-2026-0543）で検出したため |
| 入力検証 | — | 制御文字を含む名前・名義は 422 | NUL を含む文字列が DB エラー（500）になるのを防ぐ |

## 11. v0.2 からの変更

| 項目 | v0.2 | v0.3 | 理由 |
|---|---|---|---|
| 同じ内容・別のキーの取り込み | 新しいバッチとして取り込む | 409（`allow_duplicate` で許可） | キーの付け方はクライアント次第で、同じ明細の再送が翌月の同額の請求に自動確定されうる（§5.1） |
| ロック待ち | 無期限 | 5 秒で 503（`busy`）。接続を取得できない場合も 503 | 待っている要求が接続プールを使い切り、参照と `/readyz` まで止まる（§3.1） |
| 要求の時間 | 上限なし | 30 秒で 503（`timeout`） | DB で止まった要求が接続を持ち続けないように |
| パニック | 接続が切れるだけ | 500 と `request_id`、ログに記録 | 原因を追えるように |
| 組み合わせ探索 | 最大 2^n | およそ 2^(n/2) | ロックを持ったまま、非同期ランタイムのスレッドの上で走るため（§4.3） |
| 請求が消えた候補 | `suggested` のまま残り、確定すると必ず 409 | 取消にして、入金を `unmatched` に戻す（I5） | 一覧の `suggested` を「人が確定できるもの」だけにする |
| 請求の参照 | 一覧のみ | `GET /v1/invoices/{id}` が、消し込んだ消込と入金を返す | 根拠を請求の側からも辿れるように |

## 12. v0.3 からの変更

| 項目 | v0.3 | v0.4 | 理由 |
|---|---|---|---|
| 取消の理由 | 記録しない | `matches.cancel_reason`（§4.7） | 自動の取消（I5）が加わり、人の却下と区別できなくなった |
| 再判定 | なし（§9 の拡張案） | `POST /v1/payments/rematch`。`unmatched` の入金が対象（§4.6） | 候補を失って `unmatched` に戻った入金や、別名・請求を後から登録した入金を、手動消込なしで消し込めるように |
| `decision` | 取り込み時の判定のまま | 再判定で置き換え、`decided_at` を持つ | 再判定で確定した消込の根拠を入金から読めるように |
